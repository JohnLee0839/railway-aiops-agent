## 6. 所有 State 变化

### 6.1 PlanExecuteState（旧链路）

```python
# app/agent/aiops/state.py:10-24
class PlanExecuteState(TypedDict):
    input: str                                              # 用户任务描述
    plan: List[str]                                         # 执行计划步骤列表（逐步消费）
    past_steps: Annotated[List[tuple], operator.add]       # 已执行步骤 [(step, result), ...]
    response: str                                           # 最终响应/报告
```

**状态流转：**
```
{input, plan:[], past_steps:[], response:""}
    → planner → {plan: ["step1","step2",...]}
    → executor → {plan: ["step2",...], past_steps: [("step1","result1")]}
    → replanner → {plan: [...]}  或  {response: "..."}
    → executor → ... (循环)
    → END (当 response 非空 或 plan 为空)
```

### 6.2 IncidentState（新链路）

```python
# app/models/incident.py:51-61
class IncidentState(str, Enum):
    NEW = "NEW"              # 事件创建
    TRIAGED = "TRIAGED"      # TriageAgent 完成分诊
    PLANNED = "PLANNED"      # RunbookAgent 生成计划
    EXECUTING = "EXECUTING"  # ActionOrchestrator 执行中
    VERIFIED = "VERIFIED"    # Verifier 验证通过
    RESOLVED = "RESOLVED"    # 软终态（可被补偿打破）
    COMPENSATING = "COMPENSATING"  # 补偿中
    FAILED = "FAILED"        # 严格终态
    ESCALATED = "ESCALATED"  # 严格终态
```

**合法迁移表（`app/core/state_machine.py:41-83`）：**
```
NEW       → TRIAGED, FAILED, ESCALATED
TRIAGED   → PLANNED, FAILED, ESCALATED
PLANNED   → EXECUTING, FAILED, ESCALATED
EXECUTING → VERIFIED, COMPENSATING, FAILED, ESCALATED
VERIFIED  → RESOLVED, COMPENSATING, FAILED
RESOLVED  → COMPENSATING     (软终态，允许补偿打破)
COMPENSATING → VERIFIED, FAILED, ESCALATED
FAILED    → (严格终态)
ESCALATED → (严格终态)
```

## 7. 所有 Prompt 作用

| Prompt | 位置 | 作用 | 关键特征 |
|--------|------|------|---------|
| **planner_prompt** | `app/agent/aiops/planner.py:28-59` | 制定执行计划 | 动态注入工具描述+经验文档；temperature=0 |
| **replanner_prompt** | `app/agent/aiops/replanner.py:41-88` | 三态决策(continue/replan/respond) | 硬性限制：>=5步禁止replan；决策口诀 |
| **response_prompt** | `app/agent/aiops/replanner.py:92-108` | 生成最终报告 | Markdown格式，基于实际数据 |
| **executor SystemMessage** | `app/agent/aiops/executor.py:62-73` | 步骤执行指导 | 工具使用+失败处理 |
| **TRIAGE_PROMPT** | `app/agents/triage_agent.py:25-45` | 攻击分析+影响范围 | 铁路信号领域特定，要求TopologyKB查询 |
| **RUNBOOK_PROMPT** | `app/agents/runbook_agent.py:37-73` | 处置计划生成 | 禁止硬编码，列出6个可用Mock动作 |
| **RAG SystemPrompt** | `app/services/rag_agent_service.py:171-187` | 通用AI助手 | 工具使用原则+回答要求 |

### Prompt 设计分析

1. **Planner Prompt** 最大的设计亮点是 `${experience_context}` 动态插入 —— 允许从 Milvus 检索的历史经验作为 in-context learning 注入。
2. **Replanner Prompt** 采用"决策优先级口诀"降低 LLM 继续拖延的概率，这是典型的 Prompt Engineering 防护设计。
3. **RunbookAgent Prompt** 明确规定 `严禁硬编码固定动作` 是防止 Agent 走捷径的关键约束。
4. **所有业务 Prompt** 使用 `ChatPromptTemplate` + `with_structured_output()` 双保险：既约束了格式（Pydantic Schema），又约束了内容（Prompt 指令）。

## 15. 所有关键设计思想

### 设计思想 #1: 双链路共存策略
**位置:** `app/services/aiops_service.py:38-55`

项目同时保留旧版 `Plan-Execute-Replan` (LangGraph StateGraph) 和新版 `事件驱动 Pipeline` (IncidentRouter)，实现渐进式架构演进。旧链路不删除，确保向后兼容，新链路逐步替代。

### 设计思想 #2: Agent职责原子化
**位置:** `app/agents/` 整个目录

每个 Agent 职责单一、边界清晰：
- TriageAgent 只分析不执行
- RunbookAgent 只计划不执行
- ActionOrchestrator 只执行不决策
- Verifier 只验证不路由
- Replanner 只路由不执行

这是典型的 **单一职责原则(SRP)** 在 Multi-Agent 架构中的体现。

### 设计思想 #3: LLM与规则分层
**位置:** `app/agents/verifier.py:39-125`, `app/agents/replanner.py:55-148`

Verifier 和 Replanner **不调用 LLM**，完全基于规则。LLM 只用在需要"理解"的环节（分诊、计划生成），而需要"可靠决策"的环节（验证、路由）使用确定性的规则逻辑。这是避免 LLM 不可靠性影响关键路径的设计。

### 设计思想 #4: 状态机保障一致性
**位置:** `app/core/state_machine.py:41-83`

9 状态 + 合法迁移表 + 终态语义（FAILED/ESCALATED 不可逆 > RESOLVED 可被补偿打破），确保事件处理流程不会进入非法状态。

### 设计思想 #5: KB 检索优先级硬编码
**位置:** `app/agents/runbook_agent.py:94-158`

检索优先级 `CaseKB > RunbookKB > TopologyKB` 不是让 LLM 决定，而是**在代码中硬编码**。这样可以确保 LLM 无法"跳过"更高质量的来源。

### 设计思想 #6: MCP 协议实现工具即插即用
**位置:** `app/agent/mcp_client.py:112-186`

使用 MCP 标准协议统一工具接口，本地工具和远程 MCP 工具对 Agent 透明。`MultiServerMCPClient` 支持多服务器同时连接，工具拦截器（retry_interceptor）实现统一的错误处理。

### 设计思想 #7: 故障注入实现混沌工程
**位置:** `app/tools/mock_actions.py:27-173`

`FailureMode` 支持 SUCCESS/FAILURE/TIMEOUT/EXCEPTION 四种模式，每个 Mock 动作可配置独立故障率。这是**混沌工程**思想在 Agent 系统中的体现，确保系统在真实故障场景下的鲁棒性。

### 设计思想 #8: 去重窗口的多级Key策略
**位置:** `app/events/deduplicator.py:147-183`

从 `dedup_key` → `event_signature` → `source_ip` → `metadata.source_ip` → `attack_type:train_id` → `attack_type:signal_id` → `attack_type` 逐级回退，确保在不同信息完整度下都能有效去重。

### 设计思想 #9: OpenAI兼容模式实现厂商无关
**位置:** `app/core/llm_factory.py:24-49`, `app/services/vector_embedding_service.py:20-131`

LLM 和 Embedding 都通过 OpenAI 兼容 API 调用，理论上可无缝切换到任何兼容 OpenAI API 的提供商（阿里云、OpenAI、Azure、本地 vLLM 等）。

### 设计思想 #10: 全链路审计可回放
**位置:** `app/core/audit_store.py:47-266`

每一次状态迁移、Agent 决策、工具调用都记录到 AuditStore，支持按 incident_id/trace_id/thread_id 多维度查询和完整时间线回放。SSE 事件总线支持实时订阅任意 thread 的全链路事件。
